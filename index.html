What Are Claude Skills?

A Skill is a reusable set of instructions you give Claude so it consistently performs a specialized task the right way — every time, for anyone on the team.

Think of all the domain knowledge that currently lives inside specific people's heads. A payroll engineer knows the correct way to handle a mid-period FEIN change. A QA specialist knows what edge cases to watch for in overtime calculations. A PM knows which compliance rules apply to which customer tier. Skills are how you capture that knowledge and make it repeatable inside Claude.

Why not just write a good prompt each time?

You could. But prompts are ephemeral — they live in one conversation and disappear. Skills are:

📦

Persistent

Written once, available to every Claude session on your team. No re-explaining from scratch.

🔁

Consistent

Claude follows the same process every time. No drift between how different team members ask for the same thing.

🔍

Reviewable

Skills are files. You can read them, version-control them, and update them when rules change.

🧩

Composable

Skills can reference each other and combine with agents to do larger, more complex workflows.

🧭 Who should care about this?

Everyone in the 3-person pods — engineers, QA, designers, PMs. If you're a "producer" on a pod, you need to understand what skills are well enough to either write them or meaningfully review what your engineers produce. If you're a GM or lead, you need this to evaluate whether the team is using them correctly.

The Right Mental Model

Most people on the team will initially think of Skills wrong. Here's the correction before the confusion sets in.

Not a chatbot. Not magic. A specialist you trained.

When Claude has a Skill loaded, it's not browsing a knowledge base or "looking things up." It's reading your instructions and executing them within the context of whatever you're working on. The Skill is the training. The task prompt is the job request.

Wrong mental model
Claude as search engine

"I'll ask Claude and it'll figure out the right thing to do."

Right mental model
Claude as trained specialist

"I wrote down exactly how this task should be done. Claude executes those instructions on each new case."

Skills are not prompts. They're policy documents.

A prompt says "do this thing." A skill says "here is how this category of thing should always be done, with these rules, these checks, and this output format." The distinction matters enormously in payroll and workforce domains, where process consistency isn't optional.

How Claude decides to use a Skill

Claude reads the skill's name and description, and decides whether the current task matches. This is called triggering. If the description is vague or too narrow, Claude may not reach for the skill even when it should. Writing a clear, specific description is as important as writing the skill itself.

⚠️ Common mistake

Assuming Claude will "figure out" when to use a skill. If your skill description doesn't clearly match the task vocabulary, Claude may ignore it. Specific descriptions trigger reliably. Vague descriptions don't.

The three levels Claude sees

  Skill loading layers
Always loaded
Name + Description (~100 words) — Claude sees this in every conversation. This is the trigger signal.
On trigger
SKILL.md body — The full instructions. Loaded when Claude decides the skill applies. Keep under ~500 lines.
As needed
Bundled resources — Reference files, scripts, templates. Claude reads these only when the task specifically requires them.
✓ Key takeaway

You're not "teaching Claude" in a general sense. You're writing a precise, reusable instruction set that Claude executes on demand. The clearer and more specific your Skill, the more reliable the output.

Anatomy of a Skill

Every skill lives in a folder. The folder has a required file called SKILL.md and optional supporting resources. Here's what goes where.

The folder structure

Skill folder layout
my-skill/
├── SKILL.md              # Required. The brain.
└── references/           # Optional. Supporting docs.
    ├── rule-source.md    # e.g. labor law summaries
    └── output-template.md# e.g. expected output format

Inside SKILL.md

The file has two parts: a YAML header (called "frontmatter") and a body written in plain markdown.

  SKILL.md · annotated
name
A short identifier. Lowercase, hyphenated. Examples: overtime-rule-checker, payroll-reconciliation. This is how the skill is referenced internally.
description
This is the trigger mechanism. Claude reads this to decide whether to use the skill. Include: what the skill does, when to use it, and specific vocabulary it should match. Be slightly "pushy" — write as if you want Claude to reach for it whenever relevant.
Body
The actual instructions. Tell Claude what to do, step by step. Include: input expectations, output format, rules to follow, edge cases, what to do when uncertain, and when to stop and ask a human.

A minimal working example

SKILL.md · minimal example
---
name: timecard-exception-summary
description: Summarize timecard exceptions for a pay period review.
  Use this skill when someone asks to review, flag, or summarize
  timecard exceptions, missing punches, or overtime anomalies.
  Also trigger when a user mentions "pay period review" or
  "timecard audit".
---

# Timecard Exception Summary

Given a set of timecard records for a pay period, produce a
structured exception report.

## What to flag
- Missing punch pairs (in without out, or out without in)
- Shifts > 12 hours without a supervisor note
- OT hours in states where daily OT applies (CA, AK, NV)
- Duplicate punches within 5 minutes of each other

## Output format
Return a markdown table with columns:
Employee | Date | Exception Type | Details | Severity

Severity: HIGH (requires correction before processing),
MEDIUM (review recommended), LOW (informational only).

## When uncertain
If a rule is ambiguous or the data is incomplete, flag the
row with Severity: REVIEW and note what information is missing.
Do NOT infer or guess at the correct value.
💡 Notice the "When uncertain" section

This is not optional in payroll skills. Claude is very good at sounding confident. In compliance-sensitive domains, you must explicitly tell it what to do when it doesn't know — and the answer is always "flag for human review," not "make your best guess."

Writing Your First Skill

The best first skills solve a specific, repeated pain point your team already has. Not an ambitious AI workflow — a thing someone does manually every sprint and wishes they didn't have to.

Step 1: Find the right candidate

Ask yourself: What's a task someone on our team does repeatedly where the process is well-defined but execution is tedious or error-prone?

✓

Good skill candidates

Reviewing spec docs for missing edge cases. Formatting a reconciliation report. Checking if a config file follows naming conventions. Drafting release notes from a ticket list.

✗

Poor skill candidates (for now)

Anything that requires live data access you haven't wired up. Anything where "right" depends entirely on context you haven't defined. Any task that requires judgment over compliance rules without a cited source.

Step 2: Interview yourself (or the SME)

Before writing a word of the skill, answer these questions:

1

What does the human actually do today?

Walk through the manual process step by step. The skill is a translation of that process, not a replacement for thinking through it.

2

What does the input look like?

A file? A pasted table? A description? The more specific you are about expected input format, the more reliable the output.

3

What does success look like?

Define the output format precisely. A markdown table? A JSON object? A bulleted list with specific fields? Don't leave this to Claude's judgment.

4

What are the edge cases where Claude should NOT proceed?

In payroll specifically: any ambiguity in rule interpretation, missing required data, or output that would directly drive a calculation should require human review.

5

What's the source of truth for the rules?

If your skill applies any rule (overtime threshold, break penalty, FEIN logic), the source must be cited. Skills should name the rule source, not just embed the rule silently.

Step 3: Write the skill

Use this template as a starting point:

SKILL.md · starter template
---
name: your-skill-name
description: One sentence on what it does. Then: "Use this skill
  when [specific trigger phrases or task types]. Also trigger
  when [secondary triggers]."
---

# [Skill Name]

## Purpose
Brief description of what this skill is for and why it exists.

## Input expected
Describe what the user should provide. Be specific about format.

## Steps
1. First, do X
2. Then check for Y
3. Apply rule Z (source: [cite source])
4. Format output as described below

## Output format
Exact description or example of what Claude should return.

## Rules & constraints
- Rule 1
- Rule 2

## When uncertain or data is incomplete
[REQUIRED for payroll/workforce skills]
Do NOT guess. Flag the item with status NEEDS_REVIEW and
note specifically what information is missing or ambiguous.
Do not produce output that could directly drive a payroll
calculation without explicit human confirmation.

## Human review required before
[List any outputs that must be reviewed before customer impact]

Testing & Iterating on Skills

A skill you wrote once and never tested is a liability. The loop is: write → test → evaluate → improve. Repeat until the output is reliable enough that you'd stake a customer deliverable on it.

The basic test loop

1

Write 3–5 test prompts before you start

These are the real-world requests someone on the team would actually type. Include at least one "happy path" case, one edge case, and one case where the skill should refuse or escalate. Write these before testing so you aren't unconsciously biasing toward cases the skill handles well.

2

Run each test prompt with the skill loaded

In Claude Code or Claude.ai with the skill installed, paste each test prompt and record the output. Don't intervene — you want to see exactly what the skill produces unassisted.

3

Evaluate each output against your success criteria

For every test: Did it produce the right format? Did it apply the right rules? Did it flag uncertainty correctly instead of guessing? Did it trigger when it should have? Did it NOT trigger when it shouldn't?

4

Update the skill based on what failed

When a test fails, identify whether it's a description problem (skill didn't trigger), an instruction problem (wrong output), or an edge case problem (not covered). Fix the appropriate section and re-run.

Evaluating triggering specifically

The most common silent failure mode: the skill exists but Claude doesn't reach for it. Test trigger reliability by asking the same task in 3–4 different ways people on the team would naturally phrase it. If the skill only triggers on your exact phrasing, the description needs to be broader or more keyword-rich.

⚠️ Don't test with the prompts you used to write the skill

It's easy to write test cases that match how you already wrote the instructions. The skill will look great in testing and fail in production. Ask a teammate to write the test prompts, or write them before writing the skill itself.

What "good enough" looks like

For non-compliance tasks: consistent, correct output on happy path cases, appropriate escalation on edge cases.

For payroll/workforce compliance tasks: zero silent failures. Every uncertain or ambiguous case must produce a flag, not an answer. "Good enough" is higher here.

Versioning skills

Skills change when rules change. When a labor law updates, a config format changes, or an internal process shifts, the skill must be updated. Treat your SKILL.md files like code — in version control, with a change log, reviewed before deployment.

Going Further
Skills + Agents: How They Work Together

A Skill tells Claude how to do something. An Agent is Claude given permission to take action — to call tools, run code, read files, or chain tasks — using Skills as its playbook.

The difference in plain terms

Skill
Specialized knowledge

"Here's how to review a timecard for exceptions." Claude reads the task, applies the skill, returns output. Passive — Claude does not take action beyond generating a response.

Agent
Autonomous executor

"Check all timecards filed today, flag exceptions, and post the summary to Slack." Claude uses tools to do each step. Active — Claude takes real-world actions.

Why small, specific agents matter

The impulse is to build one big agent that "handles payroll." This is where things break. Smaller, scoped agents are safer because:

🎯

Blast radius is bounded

An agent that only reads timecards and produces a report can't accidentally write to payroll. Scope is protection.

🔎

Failures are easier to diagnose

When a small agent gets it wrong, you know exactly where to look. Big multi-step agents produce bugs that are hard to trace.

✋

Human checkpoints are natural

Breaking work into small agents means there are natural handoff points where a human can review before the next step runs.

A payroll-safe agent pattern

For any agent that touches payroll or labor calculations, use this architecture:

  Safe agent pattern for compliance domains
Stage 1: Read-only
Agent reads data. No writes. Produces a structured analysis using the relevant Skill. Output: a draft, not an action.
Stage 2: Human gate
A human reviews the draft output. Approves, rejects, or flags for further review. This is non-negotiable for any output that drives a calculation.
Stage 3: Write (gated)
Only after approval does a separate action step commit anything. This step should be simple and narrow — no inference, just execution of the approved output.
Stage 4: Audit trail
Every agent action is logged: what was read, what was output, who approved, what was written. This is your compliance record.
🚨 Hard rule for Payroll & Workforce agents

No agent output should directly write to a payroll calculation or customer-facing result without a human approval step in between. "Confident but wrong" is a very real failure mode for LLMs in compliance domains. The architecture must make this impossible, not just unlikely.

R365 Specific
Payroll & Workforce: Guardrails for Our Domain

The stakes here are real. Miscalculated payroll means fines and liability — for our customers and for R365. These rules are non-negotiable for any skill or agent that touches this domain.

The core risk: Confident but wrong

Claude is very good at producing authoritative-sounding output. In most domains this is fine. In payroll and workforce, it is the specific failure mode we're designing against. A confident but wrong overtime calculation doesn't look wrong — it looks like an answer. Your skill must make "I'm not sure" structurally easy to produce and "here's a number" structurally hard to produce without a cited rule.

Guardrail rules by scenario

Scenario
Rule
Risk level
Payroll calculation output
Any skill that computes earnings, deductions, or taxes
Human sign-off required before output reaches any customer-facing system. Skill must produce a flagged draft, not a committed result.
🔴 High
Labor rule interpretation
Overtime thresholds, break penalties, daily vs. weekly OT
Skill must cite the rule source (state, federal, version/date). Output must include the citation, not just the conclusion. Rules change — skills must be versioned.
🔴 High
Multi-FEIN employee identity
Person Service / cross-FEIN record matching
No automated merging of employee records across FEINs without explicit human confirmation. Flag potential matches for review; do not resolve them.
🔴 High
Timecard exception flagging
Missing punches, anomalies, OT flags
Skills may flag and summarize. They may not auto-correct timecard records. Corrections require human approval.
🟡 Medium
Scheduling rule application
Predictive scheduling, minor work rules, shift differentials
Must cite source jurisdiction and effective date. Flag when schedule data is incomplete or rule applicability is unclear.
🟡 Medium
Spec & doc review
Reviewing feature specs for missing edge cases
Lower risk. Skills can produce analysis and suggestions without human gate — but should note when a compliance question requires SME review.
🟢 Lower

Required sections in every payroll-domain skill

🚨 Mandatory — no exceptions

Every skill in the Payroll or Workforce domain must include explicit "When uncertain" and "Human review required before" sections. These are not optional polish — they are the guardrail. A skill without them should not be considered production-ready.

How rules get into skills — and stay current

Labor law changes. Tax tables update. Break penalty thresholds shift by jurisdiction. This means any skill that encodes a rule is a snapshot in time. The team needs a process — not just a convention — for keeping skills current. At minimum:

1

Rules in skills must have a source and effective date

Don't write "OT kicks in after 40 hours." Write "Per FLSA §207(a)(1) — federal standard; state overrides apply. Verify state-specific rules in references/state-ot-rules.md (updated [date])."

2

Skills that embed rules need an owner

Someone is responsible for updating that skill when the rule changes. This should be assigned explicitly, not assumed.

3

Skills in version control, treated like production code

PR review, change log, approval before merge. Especially for anything in payroll domain.
